# 무료 운영 최적화 1차

## 변경 범위

- 운영 환경에서도 warm process당 PostgreSQL 연결 풀 하나를 재사용합니다.
- 풀당 최대 연결은 3개, 유휴 연결 회수는 10초, 쿼리 제한은 15초입니다. 여러 서버 인스턴스 전체의 연결 수를 3개로 제한하는 뜻은 아닙니다.
- 공개 캠페인 조회에만 600초 Data Cache를 사용합니다. SQL과 검색 조건을 캐시 키에 포함합니다.
- 로그인 정보와 개인정보는 이 캐시에 넣지 않습니다.
- 기존 6시간 수집 작업, Neon 데이터, 운영 환경변수는 변경하지 않습니다.

## 검증

`node --test test/cost-regression.test.cjs`

풀 재사용, 바인딩, 설정 누락, 오류 전달, 캐시 키 분리, 직렬화 경계, 실패 재시도를 검사합니다. pg와 Next cache를 대체한 단위 테스트이므로 실제 Neon 연결이나 배포 환경 캐시 검증을 대신하지 않습니다. GitHub Actions에서 전체 Next.js 빌드를 추가 실행합니다.

## 배포 후 확인

1. 운영 DATABASE_URL이 Neon pooled endpoint인지 확인합니다. URL이나 비밀번호는 문서·로그에 기록하지 않습니다.
2. 동일 필터를 반복 조회하고 결과가 유지되는지 확인합니다. 다른 지역/플랫폼/페이지가 같은 결과로 섞이면 안 됩니다.
3. 수집 후 다음 캐시 갱신에서 데이터가 반영되는지 확인합니다. 600초는 재검증 기준이며 엄격한 최대 지연 보장은 아닙니다.
4. Neon compute 사용량과 Vercel 함수 사용량을 전후 비교합니다. 트래픽 측정 전에는 절감액을 확정하지 않습니다.
5. CPU/DB 사용량을 늘리는 keep-alive 요청은 추가하지 않습니다.

## 롤백

이 PR의 코드만 되돌리고 재배포합니다. DB 스키마 변경과 데이터 이전은 없으므로 데이터 롤백은 필요하지 않습니다.

## 후속 운영 원칙

Prism과 its-me의 Supabase는 유지 후보입니다. Algo-Memory의 별도 Neon 이전은 인증·계정 매핑·학습 기록 복원을 확인한 뒤 전환합니다. 유료 플랜 전환이나 기존 프로젝트 중지는 자동 수행하지 않습니다.
